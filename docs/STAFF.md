# Сотрудники и расписание

Временные слоты привязаны к сотруднику (`employee_id`). Разные сотрудники могут принимать клиентов одновременно. Пересекающиеся интервалы услуг одного сотрудника запрещены; проверка и вставка записи выполняются внутри `BEGIN IMMEDIATE`. SQLite сериализует записи во всей базе, поэтому это не горизонтально масштабируемый scheduler.

`POST /api/employees` принимает `{name}`, требует административную сессию. `POST /api/slots` принимает service_id, employee_id и будущий starts_at с часовым поясом. Для совместимости employee_id по умолчанию равен 1. Панель позволяет добавить сотрудника, выбрать его для времени записи и фильтровать расписание. `/slots` в Telegram показывает имя сотрудника и исключает время, пересекающееся с действующей записью этого сотрудника. Финальная проверка всегда повторяется при `/book`, поскольку список мог устареть.

При первом открытии исходной базы выполняется транзакционное обновление схемы до `PRAGMA user_version=2`: создаётся сотрудник 1 «Основной специалист», все прежние слоты закрепляются за ним, уникальность времени меняется с глобальной на `(employee_id,starts_at)`. Сохраняются ID слотов, записей, processed_updates и административных сессий. Проверяется foreign_key_check; ошибка откатывает миграцию. Перед обновлением остановите оба процесса, сделайте SQLite backup и проверьте восстановление в отдельный путь. Возвращать старую версию кода на обновлённую базу нельзя; для отката нужен согласованный backup.

Тесты проверяют перенос существующей записи, внешние ключи, одновременное время разных сотрудников, конфликт одного сотрудника, интервальную доступность, права API и сценарий панели. Не реализованы отпуска, перерывы, перевод существующей записи другому сотруднику и управление доступом отдельных сотрудников. Реальные Telegram polling/доставка остаются непроверенными без локального токена и двух аккаунтов.

Ruff E9/F проверяет app/tests/scripts. Строгий mypy пока проверяет типизированный модуль app/intervals.py; полная типизация всего приложения не заявляется.
